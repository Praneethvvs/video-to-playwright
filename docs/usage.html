video-to-playwright

A Claude Code skill that turns a recording of manual browser testing into a verified Playwright suite — plus a walkthrough video for human sign-off.

What it does

Someone records themselves doing a manual test pass. The skill turns that into automated browser tests, and produces one video so the person who made the recording can confirm the tests really do what they demonstrated — without reading any code.

The reason this needs a method rather than a prompt: a recording tells you what a human did and why, but it cannot tell you how to address anything in code. Pixels carry no element names. So three sources get joined, and keeping them separate is the trick:

SourceGives youCan't give you
Video framesthe sequence, the screen at each stepdurable locators
Narration / transcriptintent, expected results, business rules, prerequisitesanything not said aloud
App source + running apphow to address every elementwhich flows anyone cares about

The one rule

Never ship a test containing a locator or assertion that hasn't been executed against the running application. A plausible-looking test that was never run is worse than no test: it reads as coverage, passes review, and fails silently later.

The corollary matters as much: never invent an assertion to fill a gap. If the recording doesn't say what "correct" means, that becomes a question for a human. If nobody answers, it becomes an honest hole in the traceability matrix. An honest hole is visible and fillable; fabricated coverage is invisible until it costs you a release.

There's a subtler version of the same mistake, and it strikes while you're looking at the real app: you notice something true — exactly one option is selected, there are three rows — and assert it. But true on the day I looked is not a requirement. Nobody asked for it, so nobody recognises it when it breaks, and on shared data it will break with no defect present.

How to use it

No special command — point Claude Code at the files and ask in plain language:

Here's a recording of our release checks: recordings/checkout-flow.mp4,
and the transcript recordings/checkout-flow.vtt. I need a Playwright suite
for this, and a video I can show the tester.

What it will ask you

It asks after watching the footage, batched, with its best guess attached — so answers are usually one word. Expect three questions per checkpoint in the flow:

  • What exactly were you checking here? "A banner appeared" / "it said this precise text" / "the row reached this status" are three different tests with three different values.
  • Where did this data come from? The recording shows the result of setup it never captured.
  • What would you have called a failure?

Answering those is what separates real tests from green-forever tests. Budget roughly 30 minutes.

Two things to have ready

  1. A .vtt transcript, not just .docx. Teams exports both. The .docx typically collapses the whole session to one timestamp; the .vtt has per-cue times, which is what lets narration be aligned to frames automatically. Highest value-per-word thing you can supply.
  2. Any file the flow uploads. A recording shows the file picker's result, never the file itself. Without the fixture, that step can't be automated.

Guidance for whoever records

Do thisWhy
Keep the browser address bar visibleThe URL carries the real record IDs the tests need to seed or deep-link to — the single highest-value data in a recording.
Narrate what you're checking, not just clickingNarration is the only source of assertions. "Now I verify the total matches" becomes a real test; silence becomes a test that can't fail.
Record at 1080p+, full window, no scalingCompressed captures of dense tables are unreadable, and that's where the values are.
Pause briefly before and after each clickFrame sampling misses fast transitions.
Don't cut the waitsA long wait marks where a background job runs — that's information.
One flow per recordingKeeps the step list segmentable.

Silent recordings work, but cost about twice as much. With no narration, every assertion has to come from a review conversation instead of the artifact. A single typed line per recording — "what I'm checking: the total matches the line items" — recovers most of it for ten seconds of effort.

The workflow

  1. Gather inputs and clarify. Video path, a URL to test against, where tests should live.
  2. Probe the media. Duration, resolution, and crucially whether the audio contains speech.
  3. Extract frames. Scene detection plus uniform coverage, then precise grabs where values matter.
  4. Read the transcript. Split into prerequisites, actions, expectations, business rules.
  5. Draft the spec, gaps left as gaps. Then ask the open questions in one batch.
  6. Build a locator vocabulary from the app's source, if available.
  7. Verify every locator against the running app. Where most of the real work is.
  8. Write the tests — page objects for intent, helpers for framework quirks.
  9. Run the loop until green. Expect several rounds; the first draft is always partly wrong.
  10. Record one walkthrough video in the recording's order.
  11. Hand off a traceability matrix with an explicit covered/total count.

Realistic numbers

On a 10-minute narrated recording of a single screen, in testing: 27 of 37 narrated claims automated, 20 passing tests, 8 open questions, and a walkthrough video — in roughly 90 minutes of machine time, still needing a human review pass.

"Point at a video, get a suite" is not the target. "Point at a video, get a reviewed draft plus a verification video" is — and that's still a large win over writing them by hand.

The gotchas file is the most reusable part

references/gotchas-web-frameworks.md documents locator traps that silently break the obvious approach, each with the measurement that demonstrates it. A sample:

  • Off-screen grid columns are usually still in the DOM — and how to tell "scrolled away" from "genuinely absent", which is the difference between a locator bug and app drift
  • Pinned grid columns split one row across three DOM elements sharing a row-id
  • DOM order is not display order, so never address rows by index
  • Dropdown options are portalled out of the dialog that opened them
  • [role=dialog] nodes persist after closing — assert hidden, not absent
  • Toast containers may be mounted on demand, which breaks negative assertions confusingly
  • Generated ids regenerate every render
  • A missing aria-label proves nothing — for most roles the name comes from text content
  • expect.toPass() is JavaScript-only, and what to use in Python instead

Honest scope

The method is framework-independent, and the media and transcript scripts work on any recording. The gotchas are only as general as the libraries they name.

They were measured on a React app using AG Grid, a Base UI-family component library and Sonner toasts, against an environment that required no authentication. Genuinely unexercised: SSO / storageState login flows and role-gated UI; apps whose routes carry no state, so nothing is deep-linkable; iframes, multi-tab flows, native OS file dialogs, canvas-only interfaces; TypeScript projects.

Treat the gotchas file as a starting checklist, not a specification. When your stack differs, the categories still apply — portalling, virtualization, generated ids, mount-on-demand containers, strict-mode duplicates — but the specifics will not. Measure, don't assume.

Then write down what you find. If you spend an hour discovering how some library virtualizes, append it with the measurement that proves it. This reference only becomes genuinely general by accumulating real measurements from real apps. Pull requests adding measured gotchas for other stacks are the most valuable contribution you can make.

FAQ

Can it do it fully automatically?

No, and it shouldn't pretend to. Two things can't be automated: what "correct" means at each step, and the setup state the recording never captured. Both need the person who recorded it.

Does this replace manual testing?

No. It replaces the repetitive re-verification of flows already checked once. Exploratory testing and judgement still need a person.

Are the results end-to-end tests?

Usually not in the strict sense. They hit the real UI, API and database with nothing mocked — but they tend to deep-link past the setup steps rather than clicking through them, which makes them integration tests of a screen. Say so rather than overclaiming; overclaimed coverage is how teams stop trusting a suite.

Does the model matter?

Less than the loop around it. In development the first draft of the locators was substantially wrong, and only became correct after roughly six runs against the real app. Any capable model with the same harness should land in a similar place. The durable assets are the gotchas file and the discipline.

How much maintenance?

Real data point: during development the app under test changed four times in three weeks — a new grid, a new tab, a renamed column, a renamed record. Two of those broke tests, and both breakages were caused by assertions that encoded incidental state rather than requirements. Put the suite in CI, or drift surfaces the day before a release instead of the day it happens.
